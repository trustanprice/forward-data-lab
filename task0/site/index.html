A field test of naive top-k retrieval

The evidence was already there. Nothing used it.

I tested Asta against Google Scholar on a real research question, found a specific gap in how it weighs evidence, then built a minimal version of its pipeline — small enough to fully inspect — and ran it live to see whether the gap actually shows up.

By Trustan Price, University of Illinois Urbana-Champaign — built with the same instinct that shaped a 100%-audit-coverage push at Caterpillar and a failure-detection model for NBA predictions: don't trust a pipeline until you've verified what it's actually doing.

01 · testing asta vs. scholar

I ran the same natural-language research question through both Asta and Google Scholar. Scholar returned nothing — "did not match any articles" — until I manually rewrote it as a keyword string. Asta did that rewriting itself, silently, before searching a corpus of 12M+ papers.

02 · under the hood

Asta's own step log reveals the real pipeline: reformulate the query, retrieve broadly, rerank, then cap the pool to roughly 50 papers before writing a single sentence. Every citation I checked was real — not hallucinated. But nothing after the cap step verifies the shortlist is actually right.

03 · the gap that motivated this

Asta surfaces citation counts if you go looking — a 3-citation 2026 paper and a 16,950-citation 2020 paper both sit in its source list. In the generated narrative, they're treated as equally strong evidence. The data to tell them apart was there the whole time, unused.

So I built a minimal version of that same retrieve → rerank → cap → generate pipeline — and ran it live against Claude Opus 5 to see whether the same gap shows up.

    What this doesn't fix

    1. At top_k=5 instead of 8, the seminal paper — rank 6 by pure similarity — is excluded from the candidate pool before reranking ever runs. Verified directly: it can't rescue what similarity already cut.
    2. Its effect on the generated narrative was smaller than its effect on ranking in this test — likely because citation counts are already visible as plain text in the model's context, regardless of numbering order.

    Design review — questions I pushed on

    Questions I asked

    Building this surfaced real tradeoffs worth interrogating — including a few places where my first instinct about how these fixes actually work turned out to be wrong.

    No — retrieval runs on embedding similarity alone; citation count never enters into which papers make top-k. Only Fix 2 uses it, and only to reorder papers retrieval already found. What the off-topic query actually proves is that naive top-k has no relevance floor — it returned 8 "top" papers for the coral-reef query with similarity scores from −0.034 to 0.024, pure noise, and ranked them with the same confidence as a real match. The theoretical risk is an LLM forced to answer from those 8 irrelevant papers, producing something that reads as grounded while answering the wrong question. In the live run here, Claude Opus 5 caught the mismatch itself and declined — which doesn't make the risk fake, it means this model, this once, didn't need Fix 1 to avoid it.

    No. Fix 1 never touches retrieval or the candidate pool — the top-k list is identical whether it's on or off. It's a gate applied after retrieval runs, deciding whether the single best match found is good enough to trust at all. If the embedding model or the corpus never finds a truly relevant paper in the first place, nothing in Fix 1 rescues that — it can only decide, honestly, whether to admit the result isn't good enough.

    No — both fixes finish their work before generation starts. The real order is retrieval → Fix 1 gate → Fix 2 rerank (if enabled) → generation, last. Fix 2 decides what order the papers are handed to the model as context; it never touches a report, because at the point it runs, no report exists yet.

    α = 1 is pure similarity; α = 0 is pure citation count. A fixed 0.5 is a reasonable default, but the sharper answer: lean toward similarity for emerging or narrowly technical questions — citations take years to accumulate, so heavy citation-weighting structurally buries new work — and toward citations for "what's the standard approach" questions, or when the embedding model's precision is shaky. The more rigorous version doesn't hardcode alpha at all: it's query-adaptive, and it retrieves a wider pool before reranking, since right now Fix 2 can only reorder whatever already survived the same top-k cutoff retrieval used.

    I pushed back on my own instinct here. Lowering the threshold for presumed topic novelty is circular — you can't know a topic is under-covered without already having assessed the thing the threshold measures. It's also the more dangerous failure mode: it lets thin, tangential evidence get accepted as sufficient, producing a more convincing wrong answer instead of an honest "not enough here." The better fix is calibrating the threshold relative to the corpus's own similarity distribution rather than one hand-picked constant, and checking the gap between the top result and the rest of the pool — a real signal often stands out from its own noise floor even at a modest absolute score.

    Where this leaves things

    Retrieval is fragile. Recovery shouldn't be optional.

    Retrieval is unambiguously fragile — noise-level similarity scores on an off-topic query, visible directly in the numbers. Whether a generated report reflects that depended entirely on one model's judgment call, until Fix 1 turned it into a mechanical guarantee. Fix 2 provably reorders the ranking and protects against exclusion at the top-k boundary — but its effect on this particular model's narrative was more modest than expected. That's a real finding, not a shortcoming to hide.

    →

    Proposed next layer: faithfulness verification

    After generation, mechanically check that each inline citation's claim is actually supported by that paper's abstract — the same category of fix as Fix 1: replacing "hope the model got it right" with something inspectable and guaranteed, applied one step later in the pipeline.
